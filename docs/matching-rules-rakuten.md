# 楽天カード × 楽天市場 二重計上の判定ルール

MoneyForward ME（以下 MF）で「楽天カード」と「楽天市場(my Rakuten)」の両方を連携していると、
楽天市場での買い物 1 回が次の 2 か所に支出として計上され、家計簿上で二重計上になる。

- 楽天市場口座: 商品ごとの明細（商品名・送料・クーポンが別行）
- 楽天カード口座: 決済 1 回分の明細（合計額のみ）

本ツールは **楽天カード側の明細を「振替」に変更** し、支出を楽天市場側の明細だけに残す。
楽天市場側は商品名が分かり分類しやすいため、こちらを正とする。

このドキュメントは判定ルールの仕様を定める。

## 用語

| 用語 | 意味 |
|---|---|
| カード明細 | 保有金融機関が `楽天カード` の明細 |
| 市場明細 | 保有金融機関が `楽天市場(my Rakuten)` の明細 |
| 店名キー | カード明細の内容から作る、店舗を識別する文字列（後述） |
| 市場グループ | 同じ店名キーに前方一致し、かつ同じ日付の市場明細の集まり |
| 遅延日数 | カード明細の日付 − 市場グループの日付（日） |

## 入力データ

MF の家計簿データ（Web の入出金一覧、またはプレミアムプランの CSV エクスポート）の各明細について、以下の項目を使う。

| CSV 列名 | 用途 |
|---|---|
| `計算対象` | `1` = 集計対象、`0` = 集計対象外 |
| `日付` | `YYYY/MM/DD` |
| `内容` | 店名キー作成、前方一致判定 |
| `金額（円）` | 支出は負数、収入（クーポン値引き等）は正数 |
| `保有金融機関` | カード明細 / 市場明細の判別 |
| `振替` | `1` = 振替済み、`0` = 通常の収支 |
| `ID` | 明細の一意 ID。更新操作の対象指定に使う |

CSV は Shift_JIS（cp932）で出力される。

## 明細内容の観察結果

### カード明細の `内容`

楽天市場での決済は次のいずれかの形式で届く。

- `<店名(途中で切り詰め)> ラクテンイチバ<数字6桁>` （比較的新しい形式）
- `<店名(途中で切り詰め)>` （古い形式。サフィックスなし）

店名は全角 15 文字前後で切り詰められ、単語の途中で切れることがある。

```
例（架空）:
ショップＡ 楽天市場店 ラクテンイチバ700001
サンプル雑貨ストア公式 楽 ラクテンイチバ700002
ブックストアＢ
```

### 市場明細の `内容`

`<店名(完全)> <商品名など>` の形式。1 回の注文が複数行に分かれる。

```
例（架空）:
ショップＡ 楽天市場店 【送料無料】ボードゲーム ○○
サンプル雑貨ストア公式 楽天市場店 ベビーマット ...
ショップＣ 送料                         ← 送料は別行（負数）
ショップＣ クーポン利用(10%OFF)          ← クーポンは別行（正数）
```

### 金額と日付の関係

- **カード明細の金額 = 同じ店・同じ日付の市場明細（送料・クーポン行を含む）の合計** になる。
- カード明細の日付は市場明細より **0 日〜約 2 か月遅れる**（予約商品や発送待ちは遅延が大きい）。
- 市場明細の日付がカード明細より後になるケースは観測されていない。

## 判定ルール

### 1. 処理対象のカード明細

以下をすべて満たすカード明細を対象とする。

- `保有金融機関` が `楽天カード`
- `振替` が `0`
- `計算対象` が `1`
- `金額` が負数（支出）
- 店名キーが空でない

返金（正数）は対象外。

### 2. 店名キーの作成

カード明細の `内容` から末尾の注文番号を除去し、前後の空白を削る。注文番号は次のどちらかの形。

- ` ラクテンイチバ<数字>`
- ` <6桁の数字>`（例: `楽天ブックス 705542`）

```python
key = re.sub(r"(\s*ラクテンイチバ\d+|\s+\d{6})$", "", desc).strip()
```

### 3. 候補となる市場明細

以下をすべて満たす市場明細を候補とする。

- `保有金融機関` が `楽天市場(my Rakuten)`
- `計算対象` が `1`、かつ `振替` が `0`
  - 利用者が市場側を集計対象外にしている場合にカード側まで振替にすると、支出が消えるため
- `内容` が店名キーで **始まる**（前方一致）
- 遅延日数が `0` 以上 `LOOKBACK_DAYS`（= **90**）以下

### 4. グループ化と金額照合

1. 候補を `日付` ごとにまとめて市場グループを作り、金額を合計する。
2. 合計がカード明細の金額と **完全一致** するグループを抽出する。
3. 一致したグループが複数あれば、**遅延日数が最小** のものを採用する。
4. 採用したグループは「使用済み」とし、他のカード明細の照合には使わない。

同じ店で同額の定期購入がある場合（例: 消耗品を毎月購入）も、3 と 4 によって正しい組み合わせが選ばれる。

### 5. 使用済みグループの扱い

「使用済み」の判定には、処理済みのカード明細も含める。

- 判定前に、**処理済みのカード明細**（`振替` = `1`、または `計算対象` = `0` の支出）についても手順 2〜4 を実行し、該当する市場グループを使用済みにしておく。
- その後、未処理のカード明細を **日付の古い順** に照合する。

これにより、過去に（手動または本ツールで）振替済みにした明細の相手が、新しいカード明細と誤って組み合わされることを防ぐ。

### 6. 判定結果

| 結果 | 条件 | 動作 |
|---|---|---|
| `MATCH` | 手順 4 で採用グループが決まった | カード明細を振替に変更する |
| `AMOUNT_MISMATCH` | 前方一致する市場明細はあるが、金額が一致するグループがない | 変更しない。ログと通知で報告する |
| `NO_CANDIDATE` | 前方一致する市場明細がない | 何もしない（楽天市場以外の利用とみなす） |

`AMOUNT_MISMATCH` の主な原因は次の 2 つ。

- 市場明細がまだ MF に取り込まれていない → 次回実行時に解消する
- ポイント払いなどで金額がずれている → 手動で確認する

### 7. 振替への変更

`MATCH` となったカード明細を MF 上で振替に変更し、相手先を `楽天市場(my Rakuten)` にする。
市場明細は変更しない。

## 対象外（自然に除外されるもの）

以下は市場明細に前方一致する行がないため `NO_CANDIDATE` になり、影響を受けない。

- `楽天SP ...`（楽天ペイでの店舗決済）
- `楽天証券投信積立...`、`楽天キャッシュ チャージ`（これらは利用者が別途手動で振替を管理している）
- Amazon など他サイトの利用

## 性質

- **冪等**: 振替にした明細は次回から対象外になる。何度実行しても結果は変わらない。
- **安全側**: 金額が完全一致しない限り変更しない。誤って振替にするより、取りこぼして通知する方を選ぶ。
- **遅延への対応**: 市場明細の取り込みが遅れても、次回の定期実行で拾われる。
